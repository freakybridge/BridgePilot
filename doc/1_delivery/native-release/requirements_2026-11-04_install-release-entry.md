# 发布入口部署、GitLab 支持与高效工作流：修复计划

关联待办：TODO-055。本文是本次安装部署、GitLab 支持和工作流效率修复的唯一需求与计划记录；既有 [TODO-054 发布实现](requirements_2026-11-03_single-entry-release.md)保留原结论，不重开或改写其历史验收。

## 1. 已确认目标与本轮授权

用户于 2026-11-04 最终明确：

1. **release 的流程和用法不变，允许增加 GitLab 支持。** 执行 release 时，应默认安装／升级已经准备好发布入口；不在 release 阶段补安装。
2. 修复骨架安装／升级流程缺少发布入口部署的问题。
3. **release、骨架安装和升级均追求尽可能短且高效的工作流。** 复用有效准备、缓存和核验结果，避免重复编排、无效构建及无差异写入；必要的事务保护和最终远端核验保留。
4. 计划完善后，用户明确要求“开始吧”，授权按本计划实施；不再停留在只读规划阶段。

本次决定取代前稿“release 生产文件一律不改、GitLab 仅列不支持边界”的限制。保持的是用户命令、主要阶段和发布语义，允许为平台适配与有依据的去重调整内部实现；不重写整套发布流程。

此前已确认的使用方式继续有效：发布后仍通过现有项目目录及原启动入口使用软件，不新增独立安装包、离线发行体系或部署步骤。四项目既有业务改动、stash、用户资料、项目自有 Hook 和原生 Memory 必须保留。CausisRiskSuite 当前业务改动及原 HTTP 远端已获用户确认，不重复索取同一范围授权。

当前进入实施阶段，按已确认范围修改产品、验证并推进项目接入；发布、真实下游写入与敏感目标遵守本对话已有明确授权。此前的“三小时／60,000 token／四 Agent”是未被接受的扩大方案，不伪称为已批准预算；不把一次性开发成本描述为每次 release 成本。主对话实施，按计划进行独立只读复核，受管更新与发布仍由主对话执行。

## 3. 修复边界与传播四问

| 问题 | 决定 |
|---|---|
| 属于哪一层 | 安装就绪、GitHub／GitLab 平台适配和工作流复用属于 Forge 产品层；各项目版本／构建／产物选择属于项目自身实现；本文属于元文档 |
| 通用还是工厂专属 | 发现、归属保护、事务部署、平台选择及就绪验证是通用能力；四个项目名、私有远端、业务资源规则不得写入公共 Template 或通用分支判断 |
| 是否升版与写 CHANGELOG | 本轮只有计划，无升版。后续通用安装行为新增按实际影响更新对应原生包版本和 CHANGELOG；不因部署入口自动改业务主版本或子包版本 |
| 是否同步 dogfood | 后续公共实现／Template／Skill 变化需受管生成对应 dogfood 与分发清单；保护 BP 现有专属发布入口，禁止对工厂执行下游 adopt/apply |

保留的 release 行为：用户仍调用 `git-sync release`（批量仍为 `bridgepilot-git-sync release`），由主对话单次调用受管 `git-sync release --publication-required`。聚合预检、必要源码／版本准备、构建、提交推送、正式发布、最终核验和失败接续的语义不变；有效旧版本不覆盖、无变化不重复升版、synced 不视为 released。不在 release 时自动安装／修补入口，不增加第二条 GitLab 发布命令或外部脚本流水线。

允许的内部改动：把既有 `github::` 调用收敛到最小的平台分派边界，新增 GitLab 实现及必要的向后兼容身份字段／验证，并去除有证据的重复工作；允许调整 `workflow/src/native_release*.rs`、`core/src/native_release.rs` 及相关安装／缓存模块。BP 自有版本与产物准备规则默认不动；GitHub 已有行为和既有接续记录须兼容。不得把“流程不变”误写成“生产代码不可修改”。

新增安装逻辑不通过修改全局 baseline 判定间接改变 release 的预检语义。公共 baseline 继续表示公共资产一致；安装器额外验证发布入口，并把结果纳入自身成功条件。

## 4. 推荐实现方案

### 4.1 安装时发现并制定部署计划

在既有 `project-sync` 的零写规划中增加发布入口检查，覆盖 init/adopt/update 的统一主路径：

- 已有兼容入口：读取现有根 metadata、项目驱动源码、锁文件和目标程序，核对版本／构建入口的来源与路径，不用默认模板覆盖它。
- 缺入口：依据当前项目 INSTALL、原生 manifest 和已确认交付方式形成具体部署计划。可识别规则只给出可核验候选；未知版本来源、构建或产物范围在安装阶段一次澄清，不能硬编码项目名单或盲目打包整个目录。
- 已有自定义或冲突入口：列出精确风险及保留决定；不能因普通骨架升级替换项目所有实现。
- 非支持的平台／不完整依赖：在计划中显示明确缺口及影响，避免直到真实 release 才暴露。

沿用 safe/risk/gaps/blockers 与 aggregate fingerprint；新增输入、写集和程序字节必须参与指纹。dry-run 不建目录、不编译、不写收据、不访问发布 API。

### 4.2 部署现有 release 能消费的完整入口

坚持由安装端满足 E04 的现有入口约定，保留根 metadata 的读法；平台标识如需扩展，按 §4.4 做向后兼容，不为入口部署另造一种 release 用法：

1. **注册。** 精确维护根 Cargo.toml 的 `[workspace.metadata.bridgeforge.native-release]` 段。根已有 Cargo workspace 时只合并该段，保持其他字段及 workspace 成员语义。根不存在时，计划显式列出新增最小 metadata 载体；业务仍从自身 manifest 和原脚本构建，不把 Python 或嵌套 Rust 工程迁到根目录，不创建替代版本账本。新增载体对 Cargo 向上发现的影响必须在隔离夹具验证，不能预先假定无影响。
2. **实现。** 补齐项目所有的原生驱动源码和锁定构建入口，建议放 `scripts/release/`；具体路径随项目现有规范确认。驱动按既有 SourceIdentity / SourcePlan / Plan 协议读取项目自己的版本文件、调用既有构建入口并声明明确产物，不能只生成一份指向不存在程序的 metadata。
3. **程序。** 安装／升级阶段准备并验证发布驱动自身，产物位于 `.build/`。这一步不启动业务、不连接数据库或交易柜台、不生成新业务版本、不发布业务产物。release 中原有 build 阶段仍保留，并可按原生流程复用有效产物。
4. **升级。** 保留已有兼容的项目源码、锁、metadata 和定制；需要升级受管部分时依明确资产 id、精确 target、历史 hash 与单一 ownership strategy 进行。无有效归属证据不覆盖。

通用安装实现可复用项目模式和协议辅助代码；项目特有版本、路径及产物逻辑归项目源码。禁止恢复 `.codex/bridgeforge-version.json`、package-closures.json、项目配置迁移旁文件或版本戳，也不把这些内容塞入 hooks.json。

### 4.3 与骨架更新共用事务和验收

- 将注册段、首次部署源码和发布驱动产物纳入明确写集；apply 在锁内复核输入指纹及归属。
- 驱动构建先使用隔离候选目录，验证成功后安装到最终位置；缓存属于 `.build/`，维护源码最终归项目源码／scripts 目录。
- 事务失败恢复自身修改，保留恢复收据和外部并发改动。不得留下“metadata 已写入但程序没有部署”的成功状态。
- 就绪检查至少覆盖：metadata 格式和 argv、路径未越界、build 入口可定位、程序及源码／锁身份一致、只读 source identity 返回合法且与项目版本来源一致、版本与产物来源归属明确。
- 使用受控项目适配器的只读身份路径进行验证；不能把整个 `git-sync release` 或会构建业务产物的 prepare 当安装探针。旧自定义驱动没有可安全核验的身份能力时明确列为缺口，不擅自执行未知命令。
- 在既有安装收据内区分公共工具一致、发布入口完整和发布目标受支持的结果。字段命名在实现时按现有收据版本规则确定，不创建第二套在线状态表。
- 对本次承诺提供 release 的项目，只有入口完整且目标受当前协议支持，才能报告整体安装／升级完成。已安装公共资产但尚未具备该条件时，报告实际已完成部分和明确的 incomplete/blocked 结论；不得输出笼统成功。业务运行、鉴权、网络和真实发布结果仍单独报告，不能以安装静态就绪证明它们成功。

### 4.4 GitLab 接入同一发布流程

1. **一个协调器、两个平台实现。** 在既有调用点分派仓库匹配、正式发布基线查询、版本占用检查、创建发布、上传／关联资产、核验和未知结果核销。GitHub 实现保留原行为；GitLab 只实现同等平台职责，不复制版本选择、构建、Git 同步或整套状态机。
2. **平台和仓库身份在安装阶段确定。** 以实际 push URL、项目归属及只读平台证据确定 provider、host、项目路径，写入项目原生发布声明所承载的身份信息，不建立单独发布登记 JSON。正式发布重核实际目标，不每次重新发现平台。支持自建 GitLab 的端口与 group/subgroup 路径；不把所有非 github.com 主机猜成 GitLab。Causis 使用已确认的现有 HTTP 目标，不迁仓库，不在公共代码中硬编码该主机。
3. **兼容现有协议与恢复状态。** 当前 Plan／SourceIdentity 只含 repository，且验证限两段 GitHub 路径；实施时设计最小兼容扩展，旧 GitHub 驱动和记录默认保留原解释。平台／host／project 身份绑定到指纹、固定提交和接续检查，目标漂移即拒绝；未知字段／协议版本不能静默忽略。
4. **发布与资产。** 接入实际 GitLab 支持的 Release、tag 和资产接口。推荐优先使用可核验的项目 Generic Package 存储加 Release 资产链接；在实现前确认该实例支持和启用情况。若仅支持其他官方上传接口，先证明权限、持久性、内容核验与接续同样满足要求，再采用最小适配；不为未知能力堆叠未经验证的兜底。
5. **真实完整性。** 固定 tag 对应的 commit，核对 Release 身份、精确资产集合、大小及 SHA-256。GitLab 不能直接照抄 GitHub 的 `state/digest` 字段判断；优先复用可信服务器返回的摘要，摘要无法取得时读取资产内容计算并核对，不以链接存在或本地自报哈希代替远端验证。一次事务内同一不可变资产的结果可复用；外部变化或新发布必须触发必要复核。
6. **先暴露确定失败，再做高成本工作。** 已知平台不支持、鉴权／权限不足、版本被占用时，在原聚合预检／源码准备阶段提前停止，避免业务全量构建或提交推送后才暴露。安装不通过创建真实 Release 测试权限；发布鉴权检查与第一次必要 API 访问合并，除非实际缺口，不另加独立登录检查轮次。
7. **鉴权与接续。** 使用该主机已配置且获准的凭据来源；不假定 Git push 的凭据就是 Release API 令牌，不跨主机复用 GitHub 凭据，也不在 URL、日志、源码或收据中保存令牌。读取可有界重试；写入结果未知先按操作标识、tag、Release、资产及固定提交核销，禁止盲目重复上传或覆盖。失败保留原操作记录，复用现有接续入口。
8. **同一完成标准。** GitLab 也只有 `status=released` 且 `publication_verified=true` 才完成；返回固定 commit、tag、真实 Release URL、资产核验结果。不能把仅创建 Release、仅 push 或不完整上传视为成功。GitLab 缺少某个 GitHub 特性时，按自身 API 完成等价保护；不虚构 draft／事务原子性，部分失败必须明确保留 incomplete 状态。

官方依据（仅确认通用 API，未证明 CRS 实例当前可用）：[GitLab Releases API](https://docs.gitlab.com/api/releases/)说明发布、资产链接及认证；[Generic packages](https://docs.gitlab.com/user/packages/generic_packages/)与[支持的包摘要](https://docs.gitlab.com/user/packages/package_registry/supported_functionality/)用于确定资产存储和校验方案；[Release fields](https://docs.gitlab.com/user/project/releases/release_fields/)说明发布资产链接与下载路径。

### 4.5 两条流程的最短工作路径

**安装／升级：**批次级核定一次来源与公共准备产物 → 每项目一次对外计划（含入口与平台）→ 仅补失效准备 → 同一事务 apply → 一次聚合安装验收与收据。已有计划在授权仍匹配时复用；锁内指纹复核继续保留，外层不固定再跑整套 planner／doctor／self-test。

**release：**一次受管 CLI → 原有聚合预检与平台目标检查 → 复用或准备必要版本／产物 → 原有受管提交推送 → 对应平台发布／复用 → 一次最终聚合远端核验与收据。平台调用并入这些现有阶段；外层不增加 preflight、普通同步、手动打包、gh/glab 发布或二次验收调用。

| 场景 | 必须复用／减少的工作 | 仍须保持的有效性条件 |
|---|---|---|
| 多项目同批骨架升级 | 官方来源解析、公共源码投影、CLI/Hook 构建与准备收据批次复用，不逐仓追随上游或重编公共工具 | 固定来源与公共身份不变；项目指纹、归属与路径逐仓核对 |
| 同版本无差异安装／升级 | 不 clone、不编译、不替换相同文件、不改写成功收据来制造变化；不跑业务回归或应用 | 必要来源查询最多一次／批次；真实差异与运行时身份必须仍能验证，未知状态不能当 no-op |
| 仅部分入口或依赖变化 | 只准备受影响驱动；复用源码、锁、配方、工具链／环境身份和产物哈希均匹配的缓存 | 不只看时间戳或版本字符串；需要业务构建的内容不提前塞进安装 |
| release 有变化 | 源码／版本及必要验证结果仍有效时复用；只构建真正失效的输入，不固定追加全量回归 | 版本变化影响嵌入资源／二进制时必须重建；不为追求“一次构建”发布旧产物 |
| 无代码变化且已有正式 Release | 复用原版本、tag、commit 和资产，不重新打包上传；只做必要源码增量同步及原正式发布核验 | 外部 Release／tag／资产可能变化，不能拿本地缓存代替当前远端证明 |
| 已提交、推送或部分上传后接续 | 按已有阶段核销并补缺，复用固定提交、已核验产物和远端对象；不重复升版、提交或整批重发 | 状态未知先查询；冲突对象保留，不自动删除覆盖 |

只读本地输入解析、可并行的独立查询和哈希可有界并行；依赖步骤、同仓写入、共享缓存事务和平台写入保持正确顺序。不以减少一次调用为由隐藏失败、跳过输入漂移检查或削弱最终完整性核验。

实现前在同一机器、固定来源／项目样本与网络条件下记录基线；实施后用同一方法对照。指标至少包含从指令到最终结果的墙钟耗时、各阶段耗时、子进程／Git／网络调用数、Cargo 调用数、上传数、缓存命中与实际写文件数。区分冷启动、热缓存、无变化、局部变化、失败接续；阶段耗时有包含关系时不相加，批量并行取实际总耗时。目标是消除可避免的重复成本，未测量前不承诺固定秒数或提速比例。临时性能探针使用后清理，保留必要结果证据与恢复现场。

基线必须工作量等价：不能将此前四仓“缺入口立即失败”的零构建耗时与新流程的成功发布直接比较，也不能把旧安装缺少入口验证的省略成本当成优化收益。现有 GitHub 成功路径用于无回退对照；新增 GitLab 没有同功能旧基线时，用必要调用上界、缓存／无变化场景和重复工作消除证据验收，不虚报提速百分比。

## 7. 验证矩阵与交付标准

下列为验收标准；已执行结果记录在实施记录，未记录通过的项目均仍未验证：

1. 全新无根 Cargo 项目：部署完整入口，保持原生业务构建位置；嵌套 Rust workspace 不受新 metadata 载体影响。
2. 已有 Cargo 项目及 BP：保持 workspace 字段、成员关系、原驱动和版本语义，不重复生成第二份入口。
3. 旧骨架升级：从“CLI/Hook 齐全、发布入口缺失”的现场一次升级到入口完整；重复升级无差异、不重编已匹配的驱动。
4. 项目定制保护：已有源码或注册被项目修改、未知归属、软链接／越界路径时不覆盖，并列出具体阻点。
5. 原子失败：驱动构建失败、只读身份失败、安装中断、候选输入漂移或并发改动时不宣称成功，恢复本事务原字节。
6. 就绪语义：入口缺失、程序漂移、不支持目标在安装阶段暴露；不以仅公共 baseline.clean 覆盖这些失败。
7. release 用法和主流程不变：通过原单入口验证版本选择、源码事务、发布复用、失败接续及资产保护；安装动作仍不进入 release。旧 GitHub 驱动、收据、续跑状态与 BP 行为兼容。
8. GitLab 功能：自建 host／端口／子组路径、准确仓库匹配、首次发布、已有版本复用、源码净差异升版、受保护 tag／权限不足、精确资产集合／摘要、链接重定向边界、目标漂移和 API 不兼容。
9. GitLab 恢复：上传成功但响应丢失、部分上传、Release 创建后中断、tag 或资产冲突、提交成功但 push 失败；核销后仅补缺，不重复升版、覆盖已有对象或误报成功。
10. 效率：同机同输入前后测量 §4.5 的五类场景；断言无变化 0 构建／0 上传／0 无差异替换等结构性目标；必要 API 及安全复核保留，记录真实收益或未达标原因。不得用跳过测试／摘要／版本占用检查换取提速。
11. 四项目真实闭环：安装阶段核对业务文件、自有 Hook、HEAD、索引和 stash 保护；发布阶段允许受管事务产生已授权版本／提交变化，要求 stash 和无关资料仍保留、最终 Git 与远端收据相符，不把“发布后 HEAD 不变”设为错误验收条件。CRS 必须实际验证 GitLab 发布和资产；尚未完成时不得宣称四仓全部通过。
12. 独立复核：实施后复核职责边界、受管资产归属、部署事务、两个平台的恢复语义和性能证据；本计划阶段不提前启动或宣称通过。

交付分别记录源码、产品传播、dogfood、隔离 fixture、真实下游、runtime 六类证据。缺失的证据明确标为未验证；安装运行时核验与业务应用运行不得混称。没有真实发布收据时不报告版本已发布。

## 8. 风险、停止点和未决边界

- **Causis 实例兼容与鉴权：**GitLab 支持已在范围内，不再作为“本计划不解决”的边界。当前仅确认平台类型；实施前优先只读核对实际 API、资产存储及授权能力，缺凭据或服务条件时准确报告，不猜令牌、不改远端、不擅自安装／升级服务器。必要登录由用户完成；已有内容与目标授权不重复问。
- **配置不等于程序部署：**只加 Cargo metadata、只改 Skill 提示或只加 readiness 检查均不构成本需求完成。必须交付真实驱动、必要源码／锁及受管安装路径。
- **既有业务与资料：**当前四仓都有既有改动，不能为便于安装重置、stash/pop、清理或全量归档。BridgeLibrary 工具资产与私有资料发布范围需分别明确；不从私有仓库属性推导新增资料包授权。
- **原生载体兼容性：**本方案仍保留现有根 Cargo metadata 入口约定。若隔离验证证明新增载体会改变业务 Cargo 解析，停止该项目安装并报告，不能借 GitLab 适配私自迁移业务工程或扩张入口查找语义。
- **效率与正确性：**缓存不等于永远有效。版本、源码、锁、配方、环境、权限或远端对象变化时只使相关证据失效；不能跨项目复用业务产物，不能用旧远端成功结果放行当前发布。重复查询的消除必须有同一身份和生命周期的依据。
- **网络与身份：**安装就绪不保证未来网络、凭据、远端权限或服务可用。不在安装时执行真实 release 探测，不输出或复制凭据。
- **授权与预算：**最新“开始吧”授权实施，沿用本对话有效范围。工厂正式分发、真实下游安装／发布分别复用仍匹配的授权，实质范围变化才补充，不把此前未批准的大改造预算当作有效决定。
