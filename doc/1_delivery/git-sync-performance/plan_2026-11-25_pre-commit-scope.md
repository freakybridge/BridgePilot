# git-sync 优化计划：精简提交检查与发布接续

2026-11-25，用户撤回本方案的实现，保留本文供历史查阅。后续以开发前提交 `29f305f` 为基准，逐项选择并直接退役检查。

## 为什么改

当前[公共 Hook](../../../source/forge/templates/.githooks/pre-commit)每次提交都会查指令、配置、工作区及暂存区的公共文件、编码、项目结构和 Skill。[项目结构检查](../../../source/forge/checks/src/project_structure.rs)会读取工作区的活动文档，因此与本次提交无关的旧链接也能阻断提交。2026-09-02 至 11-24 的可核实记录里，至少 24 次提交被拦截，其中 13 次涉及文档、待办或目录。完整执行次数未知，实施前另测耗时基线。

StratusAgent 面板发布的第一次失败发生在提交文档检查。修好链接后的重试以及后来的 CausisData 发布，则被同一份旧记录挡住。后一次预检看到 `source-uncertain`（上次源码提交结果不明）便退出，尚未调用 Git Hook。两类失败各用一个场景验收。

## 普通提交和同步

| 检查项目 | 计划采用的触发条件和范围 |
|---|---|
| 文本编码、产物和测试文件位置 | 每次从 Git 暂存区取得变更清单。对新增或改动的文本查编码，对新增、移动或修改的路径查目录规则。 |
| 文档中的本地链接 | 从公共 `pre-commit` 移除。即使本次新增或修改了链接、删除或改名了目标文件，Hook 也不检查链接目标是否存在，不反查哪些文档引用旧路径。已有链接核验保留在显式专项检查中。 |
| 文档索引、目录和待办表 | 文档新增、移动或删除，或索引本身有改动时，核对相关索引和目录。待办表有改动时检查该表。 |
| AGENTS、Skill 和 Hook 配置 | 变更涉及时，检查 AGENTS 分区、Skill 名称与说明、Hook 配置格式和登记规则。提交模式同样跳过 AGENTS 和 Skill 文档中的本地链接检查。 |
| Forge 公共文件一致性 | 从公共提交 Hook 移出工作区、暂存区两次全量比对。骨架升级和显式全库检查继续提供完整核验。 |
| BridgePilot 工厂版本和分发清单 | 在工厂自有扩展中按版本、模板、受管源码和分发输入触发对应检查；正式发布时完整核验。各下游的自有扩展由对应项目决定。 |

有改动时，[同步程序](../../../source/forge/workflow/src/git_sync.rs)还会在 `git add .` 前自行比对整套公共模板。普通同步和 release 共用这段代码，因此须同时调整 Hook 和同步程序，才能真正消除重复。核对现有调用条件，分别验证业务仓库与工厂路径。涉及公共受管资产的改动按实际影响检查；完整模板比对由骨架升级、显式专项检查承担。

普通同步保留范围审阅和有实际内容的提交说明，继续按项目约定撰写说明。机器按用途解析类型：当原生发布适配器需要据此判断升版级别时解析一次；已取得分类结果的源码同步阶段直接复用。纯文档、已有候选版本、无需新建提交等情形沿用各自原生规则。实施时一并核对[通用项目适配器](../../../source/forge/workflow/src/project_release.rs)和 [BP 自有适配器](../../../source/orchestrator/install/release_source.rs)对当前说明及历史提交的用法。

## 正式发布的七类检查

| 环节 | 优化后的行为 |
|---|---|
| 1. 发布目标和并发 | 保留项目、分支、实际推送目标、未解决的 Git 冲突及发布锁检查。 |
| 2. 上次发布进度 | 取消仅凭 `source-uncertain` 就退出的规则。遇到旧记录时按下表核对，只执行尚未完成的步骤。 |
| 3. 版本与标签占用 | 保留远端正式版本基线、变更分类和目标标签占用检查。重试复用合理候选版本，纯文档同步按原生规则复用已发布版本。 |
| 4. 本地发布包 | 保留产物清单、大小、摘要及源码一致性检查。准备、提交或上传期间如输入发生变化，原包不能作为新源码的成品。 |
| 5. 提交说明和模板 | 采用上节的统一规则。业务提交路径移出整套模板比对；版本判定所需的说明校验由适配器负责。 |
| 6. 源码推送 | 保留固定提交号、推送目标、工作区及本地和远端同步结果的核对。 |
| 7. 正式发布结果 | 保留 GitHub 和 GitLab 的远端标签、正式 Release、附件清单与内容核验。完成标准仍是收据同时报告 `status=released` 和 `publication_verified=true`。 |

### 旧发布记录如何处理

现有[发布入口](../../../source/forge/workflow/src/native_release.rs)先拒绝不确定状态，随后才判断记录是否过时；[旧记录判定](../../../source/forge/workflow/src/native_release_source.rs)又要求状态已经是 `pushed` 且有固定提交号。仅调换两行判断顺序无法处理实际案例。实施时复用现有锁、提交保护记录、原生版本事务和平台查询，读懂现有记录格式；先只读核对，确认处理分支后再归档旧尝试并原子保存新进度。

| 查到的事实 | 处理方式 |
|---|---|
| 能证明提交前被拦；本地及远端分支未推进，目标版本也未被占用 | 保留旧记录及失败原因，使用原候选版本重新准备修正后的内容，再提交发布。 |
| 已生成能与旧记录对应的本地提交，或远端已包含该提交 | 从推送或发布阶段继续。远端只有部分附件时，核实已存在的内容后补齐缺项。 |
| 远端已有正式发布，标签、提交和附件均符合这次已有证据 | 复用远端结果并记录核验依据，避免重复创建标签或上传附件。 |
| 同版本已由另一份内容发布，而本轮是后续的新改动 | 分别识别旧尝试与本轮候选。确认目标仓库、分支历史、原生版本事务和提交保护记录均允许开始新尝试后，归档旧记录，以远端正式版本为基线重新判定本轮版本。旧标签和附件按原样保留。 |
| 本轮仍要发布已被不同内容占用的版本，或无法确认分支、提交、附件、未完成事务或远端状态 | 暂停依赖这些事实的写入，收据指出具体冲突、已确认的事实和所缺证据。网络或权限错误不能当作“远端不存在”。 |

## 实施和验收

| 优先级 | 拟改位置和动作 | 完成标准 |
|---|---|---|
| P0 | 在隔离仓库记录现有 Hook 和受管同步的检查项、调用次数、退出码与耗时；另复现面板提交失败后的重试，以及同一仓库里后续任务遇到旧记录的情况。 | 固定普通代码、报告改名、部分暂存和中断发布的输入。用相同环境、重复次数和缓存条件对比改前改后的耗时中位数；分别记录 Hook、同步和发布预检，列明远端读写次数。 |
| P1 | 调整公共 Hook 和 Rust 检查入口，复用[编码检查](../../../source/forge/checks/src/encoding.rs)、[产物布局检查](../../../source/forge/checks/src/artifact_layout.rs)及[Skill 校验](../../../source/forge/checks/src/skill_metadata.rs)。按暂存清单选择检查，使用 Git 索引中的文件内容及路径判断结果。 | 暂存文本出现违规编码、源码目录混入产物时仍会拦截。只在工作区修好编码而未重新暂存时，仍按待提交版本报错。空暂存区能正常处理。 |
| P1 | 从提交路径移除本地链接核验，覆盖项目结构、索引、AGENTS 和 Skill 检查入口。保留目录、索引登记和元数据检查。 | 在其余规则均满足时，分别提交三种变更：报告改名而计划仍指向旧名、新增文档含无效本地链接、Skill 文档引用不存在的参考文件。三种提交均应通过，核对 Hook 执行路径中没有链接扫描。显式运行项目结构全量检查时，仍能检出活动计划中的旧链接。 |
| P1 | 调整普通和发布共用的提交路径，移出全量模板比对；对照原生适配器拆清提交说明与版本分类职责。 | 普通业务提交和同类 release 的源码提交阶段，全量模板比对次数均为 0；显式全量检查仍能报告模板漂移。验证普通同步、纯文档、影响运行的改动和已有候选，检查实际升版结果与分类原因。 |
| P1 | 在发布入口实现上述旧记录判定，复用 [GitHub](../../../source/forge/workflow/src/native_release_github.rs) 和 [GitLab](../../../source/forge/workflow/src/native_release_gitlab.rs) 的平台核验能力。 | 在隔离仓库和平台样例覆盖表中每个分支，包含旧格式缺少提交号、两次接续、并发改动、查询失败和上传中断；检查固定提交号、版本、附件摘要和实际写入次数。 |
| P1 | 用 CausisData 现场特征单独验收：本机旧记录没有固定提交号，远端同名旧版本已发布，三项附件摘要都与旧记录不同。 | 新任务若有足够证据采用新版本，应能继续；若坚持用被占用的旧版本，应明确报冲突。两种情况都不能把旧记录误报为成功，旧标签及附件写入次数为 0。 |
| P2 | 同步[工厂自身 Hook](../../../.githooks/pre-commit)及受管源码镜像，通过工厂入口更新模板校验依据。核对工厂发布路径中的版本、清单检查。 | 验证模板与镜像一致、工厂专属规则仅在工厂生效。隔离升级样例保留项目自有扩展；分别从原生 Git 提交和受管同步入口验证行为。 |

## 传播范围和实施边界

公共提交与发布恢复属于 Forge 产品层，涉及公共模板、受管 Rust 源码、[git-sync Skill](../../../source/forge/templates/skills/git-sync/SKILL.md)及相应工厂镜像；工厂版本、清单和 BP 自有适配器分别归各自入口。按实际改动核对 Forge 和受影响包的原生版本，记录 CHANGELOG。真实下游升级、写入和发布分别按对应授权执行。

实施复核重点是部分暂存、模板与项目扩展边界、旧记录能否正确归属于本次发布，以及 GitHub 和 GitLab 接续是否产生重复写入。保留现有[作者身份专项恢复](../../../source/forge/workflow/src/native_release_recovery.rs)的触发条件。
