# 原生版本与开发交付

Forge 的项目版本登记、develop 收口账本、自动稳定晋级及配置化 release 门禁已经退役，不再读取或重建 bridgeforge-version.json / package-closures.json。旧收据只能作历史资料，不用于证明当前候选。

1. 沿用当前任务范围与验证证据，读取项目 AGENTS / INSTALL 的原生构建、测试和版本规则。
2. 在已有授权范围内核对原生 manifest、根 VERSION、相关依赖和锁文件。版本判级遵守 SemVer；无变化或重复执行不升版。不凭包目录自动扩张任务范围。
   BP 组合发布产品在开发收口时维护前三段；任一组件换版并纳入新 BP 组合时，BP 项目准备新的整体基础版本。子包版本仍为三段，产品第四段由 release 在提交前确定。
3. 需要版本调整时使用项目实际支持的原生入口，先核对它的行为和影响，不猜造参数；未授权发布时不提交、推送或发布。
4. 核验最终构建产物、必要检查和原生版本一致。没有执行的运行环境或业务验收标为未验证。
5. 在当前唯一交付记录报告实际命令、结果和限制。对每个升版的产品或包，写明旧版本、新版本和具体判级依据。工程验证、用户验收与 Git 发布分别说明。

## 判级依据

Agent 按每个产品或包的公开契约独立判断。以该产品或包上次正式发布为基线，比较本次候选包含的全部改动。追加改动时复核同一个未发布候选。BP 纳入新组件时，按 BP 自身的变化判断组合版本。

- `patch` 用于兼容修复。说明修复了哪个已有行为，例如纠正现有命令偏离约定的默认行为。
- `minor` 用于兼容新增。指出用户现在能做的具体新操作，以及原有用法如何继续工作，例如新增一个可选模式。`0.x` 按公共 AGENTS 处理不兼容变更，并说明受影响的旧用法。
- `major` 用于不兼容变更。指出哪个已发布的用法、输入、数据格式或其他公开契约在升级后失效，说明影响和适用的迁移方式，例如移除已发布的命令参数。

以具体用户行为、调用方或公开契约作为依据，选择证据支持的最小升幅。改动行数、文件数和依赖的升幅只用于描述改动范围。只能证实兼容修复时判为 `patch`。公开契约范围存在歧义且会改变判级时，说明分歧并向用户澄清。

不调用已退役的 Forge develop、setup/migration/release 参数；不建立替代配置或账本，不将其搬到另一目录、改格式或塞入 hooks.json。普通 git-sync 保持可用，不主动升版。需要项目原生发布能力但入口缺失时说明具体缺口，只停止相关发布动作，不伪造 Forge 认证。
